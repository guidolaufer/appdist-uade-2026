SECCIÓN 1

Anatomía de un Composable

Jetpack Compose es un toolkit declarativo para construir UI nativa en Android, escrito completamente en Kotlin (sin XML). El cambio de paradigma es: en lugar de describir cómo construir la UI paso a paso, describís qué debe mostrar la UI según el estado actual.

Estructura básica de una función @Composable
@Composable
fun MiComponente(
    // Parámetros: datos que recibe de afuera
    nombre: String,
    onClick: () -> Unit
) {
    // Cuerpo: describe la UI
    Column(modifier = Modifier.padding(16.dp)) {
        Text(text = nombre, style = MaterialTheme.typography.headlineMedium)
        Button(onClick = onClick) {
            Text("Acción")
        }
    }
}

📋 Reglas de un Composable

Debe tener la anotación @Composable. El nombre debe empezar con mayúscula (PascalCase). Solo puede ser llamado desde otro @Composable. Puede recibir parámetros para configurar su apariencia y comportamiento.

⚡ Ventajas del paradigma declarativo

Menos código boilerplate (sin findViewById, setText, setOnClickListener). Más intuitivo y reactivo: la UI se actualiza automáticamente cuando el estado cambia. Mejor performance y mantenibilidad.

Imperativo (XML tradicional) Declarativo (Compose)
Describís cómo construir la UI paso a paso Describís qué debe mostrar la UI según el estado
findViewById(), setText(), listeners manuales Funciones @Composable que retornan UI
El programador actualiza la UI manualmente La UI se actualiza automáticamente con el estado
Mucho código repetitivo (boilerplate) Código conciso y expresivo
UI = código_imperativo() UI = f(estado)

SECCIÓN 2

Estado en Compose

Principio fundamental

En Compose, UI = f(estado). Cuando el estado cambia, Compose re-ejecuta las funciones @Composable afectadas (recomposición) y actualiza la UI. El estado debe estar en una variable observable con remember { mutableStateOf() }.

Las tres formas de declarar estado observable
// Forma 1: valor simple — por delegación (más concisa)
var contador by remember { mutableStateOf(0) }
// Uso: contador++  (se lee y escribe directamente)

// Forma 2: valor simple — sin delegación
val contador = remember { mutableStateOf(0) }
// Uso: contador.value++  (necesita .value)

// Forma 3: lista mutable observable
val lista = remember { mutableStateListOf<String>() }
// Uso: lista.add("item")  lista.remove(item)  lista.removeAt(i)
Patrón Sintaxis Cuándo usar
mutableStateOf var x by remember { mutableStateOf(valor) } Un valor primitivo o String
mutableStateListOf val lista = remember { mutableStateListOf<T>() } Lista que Compose puede observar por cambios
Sin remember ❌ var x = mutableStateOf(0) Nunca — se reinicia en cada recomposición
mutableListOf ❌ val lista = remember { mutableListOf<T>() } Nunca — Compose no detecta cambios en la lista
❌ Incorrecto — var sin remember
@Composable
fun Contador() {
    var cuenta = 0  // ❌ Se reinicia en cada recomposición
    Button(onClick = { cuenta++ }) {
        Text("$cuenta")
    }
}
✅ Correcto — con remember
@Composable
fun Contador() {
    var cuenta by remember { mutableStateOf(0) }
    Button(onClick = { cuenta++ }) {
        Text("$cuenta")
    }
}

SECCIÓN 3

Recomposición y Ciclo de Vida

🟢
Entra en composición
El composable se ejecuta por primera vez y aparece en la UI
🔵
Recomposición
Cuando el estado que lee cambia, Compose vuelve a ejecutar SOLO las funciones afectadas (smart recomposition)
🔴
Sale de composición
El composable se elimina de la UI (ej: navegación a otra pantalla)
Smart Recomposition

Compose es inteligente: solo recompone lo que realmente cambió. Si tenés 20 ítems en una lista y cambia uno, solo ese composable se re-ejecuta. Esto hace que Compose sea muy performante. No debés hacer cálculos costosos ni operaciones de IO dentro del cuerpo de un composable.

❌ No hacer: lógica en el cuerpo
@Composable
fun MiApp() {
    // ❌ Esto se ejecuta en CADA recomposición
    val resultado = calcularAlgoCostoso()
    guardarEnBaseDeDatos(resultado)
    Text(resultado.toString())
}
✅ Correcto: separar lógica
@Composable
fun MiApp(viewModel: MiViewModel) {
    // ✅ El ViewModel maneja la lógica
    val resultado by viewModel.resultado.collectAsState()
    Text(resultado.toString())
}
Regla de las funciones pequeñas

Las funciones Composable deben ser pequeñas porque Compose recompone a nivel de función. Una función grande que contiene mucho estado obliga a recomponer todo cuando cambia una pequeña parte. Funciones pequeñas = recomposiciones más eficientes + mejor reutilización + más legible.

SECCIÓN 4

State Hoisting

State Hoisting (elevación de estado) es el patrón de mover el estado hacia arriba en la jerarquía de composables para hacer los componentes más reutilizables y testeable.

Principio

Un composable debe recibir el valor del estado como parámetro y exponer un callback para notificar cambios al componente padre. Esto hace al componente "stateless" (sin estado propio) y más reutilizable.

❌ Sin State Hoisting (stateful)
@Composable
fun CampoBusqueda() {
    // El estado está DENTRO del composable
    var texto by remember { mutableStateOf("") }
    OutlinedTextField(
        value = texto,
        onValueChange = { texto = it }
    )
    // ❌ Nadie puede leer 'texto' desde afuera
}
✅ Con State Hoisting (stateless)
@Composable
fun CampoBusqueda(
    // Recibe el estado como parámetro
    texto: String,
    onTextoChange: (String) -> Unit
) {
    OutlinedTextField(
        value = texto,
        onValueChange = onTextoChange
    )
}

// Uso desde el padre:
var busqueda by remember { mutableStateOf("") }
CampoBusqueda(texto = busqueda, onTextoChange = { busqueda = it })
Q: ¿Cuándo aplicar State Hoisting?
Cuando múltiples composables necesitan acceder al mismo estado, cuando el componente debe ser reutilizable en diferentes contextos, o cuando el padre necesita reaccionar a los cambios del hijo. En general, sube el estado hasta el ancestro común más bajo que lo necesita.

SECCIÓN 5

Scaffold y estructura de pantalla

Scaffold es el composable que proporciona la estructura base de una pantalla Material. Maneja automáticamente los paddingValues para que el contenido no quede debajo de la TopAppBar.

Estructura completa con Scaffold
@Composable
fun PantallaCompleta() {
    Scaffold(
        topBar = {
            TopAppBar(
                title = { Text("Mi App") },
                colors = TopAppBarDefaults.topAppBarColors(
                    containerColor = MaterialTheme.colorScheme.primaryContainer
                )
            )
        },
        floatingActionButton = {
            FloatingActionButton(onClick = { /* acción */ }) {
                Icon(Icons.Filled.Add, contentDescription = "Agregar")
            }
        }
    ) { paddingValues ->
        // ⚠️ SIEMPRE pasar paddingValues al contenedor principal
        LazyColumn(
            modifier = Modifier.padding(paddingValues)
        ) {
            /* contenido */
        }
    }
}
Error común con Scaffold

Olvidar aplicar paddingValues al contenido hace que la lista quede parcialmente tapada por la TopAppBar. El lambda de Scaffold siempre recibe paddingValues como parámetro — usálos en el Modifier.padding(paddingValues) del primer elemento de contenido.

LazyColumn con items y key (buena práctica)
LazyColumn(modifier = Modifier.padding(paddingValues)) {
    // ✅ Usar items() — NO forEach dentro de Column
    items(
        items = listaDeItems,
        key = { item -> item.id }  // key mejora performance
    ) { item ->
        ItemCard(item = item)
    }
}
forEach vs items()

Usar forEach dentro de un LazyColumn rompe el lazy loading: todos los elementos se crean de una vez. El propósito de LazyColumn es crear solo los elementos visibles. Siempre usar items(lista) dentro de LazyColumn.

SECCIÓN 6

Material Design 3 (Material You)

Material Design 3 es la nueva versión del sistema de diseño de Google. Introduce Dynamic Color (colores que se adaptan al wallpaper del usuario) y una personalización más profunda.

MaterialTheme

El composable raíz que provee el tema a toda la app. Contiene tres sistemas: colorScheme, typography y shapes. Todos los composables Material acceden a estos valores automáticamente.

MaterialTheme(
    colorScheme = lightColorScheme(...),
    typography = Typography(),
    shapes = Shapes()
) {
    MiApp()
}

ColorScheme

La paleta de colores semánticos. Los más usados:

primaryColor principal de la app
primaryContainerFondo de elementos primarios
secondaryColor secundario
surfaceFondo de Cards y diálogos
backgroundFondo general de la pantalla
errorErrores y validaciones
Componente Uso Parámetros clave
Scaffold Estructura base de pantalla topBar, floatingActionButton, bottomBar
TopAppBar Barra superior con título y acciones title, navigationIcon, actions, colors
Card Contenedor elevado con sombra modifier, elevation, colors
Button Botón relleno (acción principal) onClick, enabled, colors
OutlinedButton Botón con borde (acción secundaria) onClick, border
TextButton Botón de texto (acción terciaria) onClick
OutlinedTextField Campo de texto con borde value, onValueChange, label, placeholder, isError
FloatingActionButton Botón flotante de acción principal onClick, dentro: un Icon
LazyColumn Lista vertical con lazy rendering modifier, dentro: items()
Jerarquía tipográfica Material 3
// De mayor a menor tamaño:
MaterialTheme.typography.displayLarge      // 57.sp — Títulos grandes
MaterialTheme.typography.displayMedium     // 45.sp
MaterialTheme.typography.headlineLarge     // 32.sp — Encabezados principales
MaterialTheme.typography.headlineMedium    // 28.sp
MaterialTheme.typography.headlineSmall     // 24.sp
MaterialTheme.typography.titleLarge        // 22.sp — Títulos de sección
MaterialTheme.typography.bodyLarge         // 16.sp — Texto principal
MaterialTheme.typography.bodyMedium        // 14.sp — Texto secundario
MaterialTheme.typography.labelSmall        // 11.sp — Etiquetas pequeñas
Contenedores: Column, Row y Box

Column: apila elementos verticalmente. Row: los coloca horizontalmente. Box: superpone elementos (útil para overlays). Los tres tienen parámetros verticalArrangement / horizontalArrangement para distribuir el espacio y verticalAlignment / horizontalAlignment para alinear.

SECCIÓN 6.5

Modifier — Estilismo en Compose

Los Modifiers son la forma de dar estilo, tamaño, comportamiento y posición a los elementos en Compose. Se encadenan con . y el orden importa.

✅ Orden correcto
Box(
    modifier = Modifier
        .fillMaxWidth()
        .padding(16.dp)    // padding fuera del fondo
        .background(Color.Blue)
        .padding(8.dp)     // padding interior
)
❌ Orden incorrecto
Text(
    text = "Hola",
    modifier = Modifier
        .clickable { ... }
        .padding(16.dp)
    // ❌ El padding está fuera del área clickeable
    // Debería ser: .padding().clickable()
)
Modifier Descripción Unidad
.padding(16.dp) Espacio interior o exterior .dp para tamaños
.fillMaxWidth() Ocupa todo el ancho disponible —
.fillMaxSize() Ocupa todo el espacio disponible —
.size(48.dp) Tamaño fijo .dp
.background(color) Color de fondo —
.clickable { ... } Hace el elemento clicable —
fontSize = 16.sp Tamaño de texto (escala con preferencias del sistema) .sp para texto
dp vs sp

Usar .dp para todo excepto tamaños de texto. Para texto, siempre .sp (scale-independent pixels): respeta la configuración de accesibilidad del usuario que puede aumentar el tamaño de fuente en el sistema. Usar .dp en texto es un error de accesibilidad.

SECCIÓN 7

Arquitectura con ViewModel

La arquitectura recomendada separa la app en tres capas. El ViewModel actúa como intermediario entre la UI y los datos.

🖥️
Capa UI
Composables que muestran el estado y capturan eventos del usuario. NO contienen lógica de negocio.
⚙️
ViewModel
Mantiene el estado de la UI (StateFlow/LiveData). Procesa los eventos del usuario. Sobrevive a rotaciones de pantalla.
🗄️
Capa de Datos
Repository, base de datos (Room), API remota (Retrofit). El ViewModel se comunica con esta capa.
Patrón ViewModel básico
// ViewModel — maneja el estado
class MiViewModel : ViewModel() {
    private val _items = mutableStateListOf<String>()
    val items: List<String> = _items

    fun agregar(item: String) { _items.add(item) }
    fun eliminar(item: String) { _items.remove(item) }
}

// Composable — solo muestra y envía eventos
@Composable
fun MiPantalla(viewModel: MiViewModel = viewModel()) {
    val items = viewModel.items
    LazyColumn {
        items(items) { item ->
            ItemRow(
                item = item,
                onDelete = { viewModel.eliminar(item) }
            )
        }
    }
}
Por qué usar ViewModel

El ViewModel sobrevive a rotaciones de pantalla (cambios de configuración). Sin ViewModel, si el usuario rota el teléfono, el estado se pierde y la UI se reinicia. Con ViewModel, el estado persiste durante todo el ciclo de vida de la pantalla.

SECCIÓN 8

Los 3 Errores Más Comunes

❌ Error 1: Estado sin remember

Declarar una variable de estado sin remember. En cada recomposición, la variable se reinicia a su valor inicial. La UI nunca refleja los cambios del usuario.

Incorrecto
var nombre = mutableStateOf("")  // ❌ Sin remember
✅ Corrección: var nombre by remember { mutableStateOf("") }
❌ Error 2: Lista sin mutableStateListOf

Usar mutableListOf en lugar de mutableStateListOf. Compose no puede observar los cambios en una mutableListOf normal, entonces la UI nunca se actualiza cuando se agrega o elimina un elemento.

Incorrecto
val lista = remember { mutableListOf<String>() }  // ❌
✅ Corrección: val lista = remember { mutableStateListOf<String>() }
❌ Error 3: forEach en LazyColumn

Usar forEach dentro del cuerpo de un LazyColumn o directamente dentro de un Column cuando se tiene una lista grande. Esto crea todos los elementos a la vez, eliminando el beneficio del lazy rendering y causando problemas de performance.

Incorrecto
LazyColumn {
    lista.forEach { item ->
        ItemCard(item)  // ❌ Todos se crean de una vez
    }
}
✅ Corrección: usar items(lista) { item → ItemCard(item) } dentro del LazyColumn
Q: Resumen rápido de errores frecuentes en el parcial
1. var x = "" sin remember → se reinicia en cada recomposición.
2. mutableListOf en lugar de mutableStateListOf → lista no observable.
3. forEach dentro de LazyColumn → no es lazy.
4. removeAt(0) en lugar de remove(item) → elimina siempre el primero.
5. División entera: a/b cuando ambos son Int → usar a.toDouble()/b.
6. toInt() en lugar de toIntOrNull() → crash con input vacío.
7. @composable con minúscula → no es válida la anotación.
8. .dp faltante en Modifier → el compilador toma el número como un tipo incorrecto.
9. Usar .sp para tamaños no textuales → incorrecto semánticamente.
10. Inicializar objetos dentro de lambdas de Scaffold → se recrean en cada recomposición.
