Ejercicio 1 — Capas de la Arquitectura Android

Mencione y explique al menos 3 capas de la arquitectura de Android. Explique de qué manera un desarrollador puede interactuar con las diferentes capas. Ejemplifique cada una.

La arquitectura de Android se organiza en 5 capas apiladas de abajo hacia arriba:

🔴 Capa 1 — Linux Kernel

Base del sistema. Gestiona drivers de hardware (cámara, audio, WiFi, Binder IPC), memoria, procesos y seguridad.
Interacción del dev: no se accede directamente desde apps. Solo fabricantes y ROM developers.
Ejemplo: el driver de la cámara vive aquí. El dev nunca lo toca directamente.

🟣 Capa 2 — HAL (Hardware Abstraction Layer)

Define interfaces estándar para que el Framework acceda al hardware sin depender de la implementación específica del fabricante.
Interacción del dev: transparente. El Framework abstrae el HAL.
Ejemplo: al usar CameraManager, el sistema llama al módulo HAL de cámara del fabricante.

🟠 Capa 3 — Libraries + Android Runtime (ART)

Librerías nativas C/C++ (SQLite, OpenGL, WebKit) y la VM ART que ejecuta bytecode .dex.
Interacción del dev: indirectamente vía Framework, o directo con NDK/JNI para C/C++.
Ejemplo: usar Room Database (que usa SQLite). Usar OpenGL para gráficos 3D con el NDK.

🟢 Capa 4 — Application Framework

APIs de alto nivel en Java/Kotlin: Activity Manager, Window Manager, Content Providers, View System, Notification Manager, Location Manager.
Interacción del dev: es la capa principal de trabajo. Se usa el SDK de Android.
Ejemplo: startActivity(intent), getSystemService(LOCATION_SERVICE), usar RecyclerView.

🔵 Capa 5 — Applications

Las apps instaladas en el dispositivo: el sistema (Teléfono, Contactos, Ajustes) y las apps de terceros.
Interacción del dev: el desarrollador CONSTRUYE la app que vive en esta capa.
Ejemplo: tu app de comercio electrónico, una app de noticias, o una app de delivery.

Resumen clave: el desarrollador trabaja principalmente con el Application Framework (capa 4) y construye en la capa de Applications (capa 5). Las capas inferiores son abstraídas por el sistema.

Descripción de cada fase

FaseHerramientaQué hace
1. Compilaciónjavac / kotlincConvierte .java/.kt a bytecode JVM (.class)
2. DEX conversiond8Convierte bytecode JVM a bytecode Dalvik (.dex), optimizado para Android
3. RecursosAAPT2Compila recursos XML (layouts, strings) y genera R.java con las referencias
4. PackagingAPK BuilderEmpaqueta .dex + recursos compilados + AndroidManifest + .so en un APK

Lo más importante: el formato .dex es exclusivo de Android. No es bytecode JVM estándar — está optimizado para procesadores ARM con memoria limitada.

Ejercicio 3 — LinearLayout vs ConstraintLayout

Compare los layouts LinearLayout y ConstraintLayout. ¿Qué diferencias conceptuales existen entre ambos y cuándo es recomendable utilizar cada uno? Justifique y proporcione un ejemplo de un uso hipotético de cada uno.

Diferencia conceptual

LinearLayoutConstraintLayout
ConceptoOrganiza hijos en UNA dirección (horizontal o vertical)Posiciona cada view en relación a otros views o al padre
JerarquíaRequiere anidamiento para layouts complejosPlana — un solo nivel, sin anidamiento
RendimientoBueno si no se anidaMuy bueno (una sola pasada de medición)
ComplejidadBaja — fácil de aprenderMayor — curva de aprendizaje
RecomendadoLayouts simples y linealesCualquier layout, especialmente complejos

¿Cuándo usar cada uno?

LinearLayout: cuando los elementos se organizan simple y linealmente, sin relaciones entre sí. Ej: un formulario de 3 campos apilados verticalmente, una barra de botones horizontal, una lista de opciones.

ConstraintLayout: cuando necesitás posicionar elementos en relación a otros, centrar elementos, crear layouts con proporciones, o cualquier diseño que requeriría anidar múltiples LinearLayouts.

Ejercicio 4 — JIT vs AOT

Explique las diferencias entre JIT y AOT. Mencione ventajas y desventajas de cada una y cuál es el modelo de runtime que hoy persiste a partir de Android 7.0 (Nougat). Tener en cuenta el consumo de CPU, memoria y experiencia al usuario al elaborar la respuesta.
AspectoJIT (Just-In-Time)AOT (Ahead-Of-Time)
¿Cuándo compila?Durante la ejecución de la appDurante la instalación de la app
Instalación✅ Rápida — no compila al instalar❌ Lenta — compila todo al instalar
Primer arranque❌ Lento — warm-up period✅ Rápido — ya compilado
CPU en uso❌ Alto — compila mientras ejecuta✅ Bajo — código ya compilado
Memoria RAM❌ Alta — compilador en memoria✅ Menor
Almacenamiento✅ Menor — no guarda en disco❌ Mayor — guarda código nativo
Experiencia usuario❌ Inconsistente (lag inicial)✅ Consistente y fluida
Optimización✅ Dinámica — aprende el uso real❌ Estática — no adapta al uso

Modelo actual: Híbrido JIT + AOT (Android 7+)

Desde Android 7.0 (Nougat), ART usa un modelo híbrido que combina ambos:

1. INSTALACIÓN: rápida, sin compilación AOT completa

2. PRIMERAS EJECUCIONES (JIT):
   → JIT compila hot code en RAM
   → Guarda un perfil de uso (.prof) en disco

3. DISPOSITIVO EN REPOSO + CARGANDO (AOT selectivo):
   → dex2oat lee el perfil
   → Compila a AOT SOLO el hot code (~20-30% del total)

4. EJECUCIONES SIGUIENTES:
   → Hot code: corre en AOT (rápido, bajo CPU)
   → Cold code: JIT bajo demanda
Resultado: instalación rápida como JIT + rendimiento en ejecución similar a AOT + menor uso de almacenamiento (solo compila el hot code). La compilación AOT ocurre cuando el dispositivo está en reposo y cargando, por lo que el usuario no lo nota.

Ejercicio 5 — HCI (Interacción Humano-Computadora)

Mencione y explique qué áreas intervienen en la investigación HCI. (a) ¿Qué diferencia y relación existe entre la UX, la UI y la CX? (b) Mencione y explique al menos 3 heurísticas de Nielsen a tener en cuenta al momento de desarrollar interfaces para dispositivos móviles. (c) Realice un wireframe de una activity en donde se apliquen los conceptos descriptos en el apartado anterior.

¿Qué es HCI y qué áreas intervienen?

HCI (Interacción Humano-Computadora) estudia cómo las personas interactúan con sistemas digitales y cómo diseñar esa interacción de forma eficiente y agradable. Intervienen: psicología cognitiva (modelos mentales, percepción), diseño gráfico (visual, tipografía, color), ergonomía (accesibilidad física, tamaño de targets táctiles), ingeniería de software (implementación) y sociología (contexto cultural, patrones de uso).

(a) UX vs UI vs CX

UX (User Experience)UI (User Interface)CX (Customer Experience)
Qué esExperiencia total de uso del productoDiseño visual de la interfazExperiencia con toda la empresa
Pregunta¿Es fácil y agradable de usar?¿Se ve bien?¿Es buena experiencia de cliente?
IncluyeFlujos, usabilidad, arquitectura infoColores, tipografía, íconos, botonesSoporte, delivery, marketing, billing

Relación: UI ⊂ UX ⊂ CX. La UI es parte de la UX, y la UX es parte de la CX. Una buena UI no garantiza buena UX. Una buena UX no garantiza buena CX.

(b) Heurísticas de Nielsen para mobile

1. Visibilidad del estado del sistema: la app siempre informa al usuario qué está pasando. En mobile: mostrar spinner al cargar datos, barra de progreso en uploads, badge con notificaciones pendientes. El usuario nunca debe preguntarse "¿qué está haciendo la app?"
5. Prevención de errores: mejor prevenir que mostrar mensajes de error. En mobile: deshabilitar el botón "Enviar" mientras el formulario está incompleto, mostrar el teclado numérico para campos de teléfono, validar email en tiempo real con indicador visual.
8. Diseño estético y minimalista: en pantallas pequeñas cada elemento compite por la atención. Solo mostrar lo necesario. Eliminar elementos decorativos que no aportan información. Usar espaciado generoso para que los elementos táctiles sean fáciles de presionar (mínimo 48dp según Material Design).
3. Control y libertad del usuario: siempre ofrecer una salida. En mobile: botón "Deshacer" al eliminar, confirmación antes de acciones destructivas, poder cancelar cualquier flujo con el botón Back del sistema.
