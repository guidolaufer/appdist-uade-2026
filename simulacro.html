Parte 2 — Preguntas Teóricas

Leé la pregunta, pensá tu respuesta y luego revelá para comparar.

1. Explicá con tus palabras qué es el Android SDK, qué es un AVD y qué es el emulador. ¿Cuál es la relación entre los tres?
Conceptos clave: SDK = caja de herramientas · AVD = configuración del dispositivo · Emulador = programa que ejecuta el AVD

El Android SDK (Software Development Kit) es el conjunto completo de herramientas que permite crear apps Android: incluye el compilador d8, las APIs del sistema (cámara, GPS, WiFi…), herramientas de línea de comandos como adb y aapt2, y las imágenes de sistema para el emulador.

Un AVD (Android Virtual Device) es un archivo de configuración que describe las características de un dispositivo virtual: qué modelo de teléfono simular, qué versión de Android (API Level), cuánta RAM y almacenamiento. No es un programa en sí mismo.

El emulador es el programa (basado en QEMU) que lee esa configuración y la ejecuta, creando un dispositivo Android virtualizado en tu PC. La relación es: el SDK provee las imágenes y APIs → el AVD define la configuración → el emulador ejecuta esa configuración.

Analogía: el SDK es la caja de herramientas del mecánico, el AVD es la ficha técnica del auto (color, motor, llantas), y el emulador es el auto en sí arrancando.

2. ¿Qué significa que Jetpack Compose sea "declarativo"? ¿En qué se diferencia del sistema de Views imperativo que usaba Android antes?
Conceptos clave: UI = f(estado) · recomposición automática · sin manipulación directa del árbol de Views

En el modelo imperativo (sistema de Views), el programador manipula la UI paso a paso: textView.text = "Hola", button.isEnabled = false. Hay que describir cómo cambiar cada elemento cuando algo varía.

En el modelo declarativo de Compose, la UI se describe como una función del estado: UI = f(estado). El programador escribe funciones @Composable que describen qué mostrar dado un estado. Cuando el estado cambia, Compose re-ejecuta automáticamente las funciones afectadas (recomposición) y actualiza solo las partes de la pantalla que cambiaron.

La ventaja principal es que se eliminan las inconsistencias entre el estado interno y lo que muestra la UI. No hace falta sincronizar manualmente.

3. Te dan el siguiente caso: "Una app de biblioteca universitaria permite buscar libros por título, marcar libros como prestados y ver cuántos libros prestados tiene el estudiante". ¿Cómo organizarías arquitectónicamente esta app en capas? Mencioná al menos un archivo/clase por capa.
Conceptos clave: capa UI · capa lógica · capa de datos · responsabilidad única

Capa de Datos:

data class Libro(val id: Int, val titulo: String, val autor: String, val prestado: Boolean) — modela el dato. LibroRepository — provee la lista de libros (desde BD local, archivo JSON o API). No sabe nada de la UI.

Capa de Lógica:

LibroLogic — funciones como filtrarPorTitulo(libros, query), contarPrestados(libros), calcularDisponibles(libros). Transforma y calcula sobre los datos. No conoce cómo se ve la pantalla.

Capa de UI:

BibliotecaScreen — composable principal. LibroItem(libro) — fila de la lista. BuscadorBar(query, onChange) — campo de búsqueda. ResumenCard(prestados, total) — card con el conteo. Solo muestra datos y captura eventos.

4. ¿Por qué no se recomienda que una función @Composable sea grande? Mencioná al menos tres razones técnicas o de diseño.
Conceptos clave: recomposición ineficiente · responsabilidad única · reutilización · Preview

1. Recomposición ineficiente: Compose re-ejecuta la función completa cuando cualquier variable de estado que lee cambia. Una función de 200 líneas que mezcla el header, la lista y los filtros se redibuja completamente si el usuario escribe una sola letra. Con funciones pequeñas, solo se re-ejecuta la función específica afectada.

2. Violación de responsabilidad única: Una función grande mezcla responsabilidades (mostrar datos, manejar input, calcular). Esto dificulta encontrar bugs y entender el código.

3. Imposibilidad de reutilizar: Un ItemCard extraído como función propia puede usarse en 3 pantallas distintas. Una función monolítica no puede reutilizarse en ningún lado.

4. Preview difícil: Una función con 15 parámetros de estado es imposible de previsualizar con @Preview. Una función pequeña con 2 parámetros se puede testear visualmente en segundos.

5. Mencioná 4 componentes de Material Design 3 que uses habitualmente en Compose y describí brevemente para qué sirve cada uno.
Ejemplos posibles: Scaffold, TopAppBar, Card, Button, OutlinedTextField, LazyColumn, Text…

Scaffold: Estructura base de una pantalla. Provee slots para topBar, bottomBar, floatingActionButton y garantiza el padding correcto para el contenido según los elementos que uses.

TopAppBar: Barra superior con título e íconos. Da contexto sobre qué pantalla estás viendo y puede incluir acciones de navegación (back) y acciones secundarias (búsqueda, menú).

Card: Contenedor con elevación y bordes redondeados para agrupar información relacionada. Puede hacerse clickeable con onClick. Usa colores del ColorScheme (surfaceVariant).

OutlinedTextField: Campo de entrada de texto con borde visible. Acepta label, placeholder, isError para mostrar errores de validación. Requiere un estado remember { mutableStateOf("") } para funcionar.

LazyColumn: Lista de scroll eficiente. Solo renderiza los ítems visibles en pantalla (equivalente a RecyclerView). Usa items(lista) con un key para optimizar recomposición al agregar/eliminar.

6. ¿Qué es el "State Hoisting" (elevación de estado) en Compose? ¿Por qué es importante?
Conceptos clave: estado en el padre · pasar valor y lambda hacia abajo · composables sin estado (stateless)

State Hoisting es el patrón de mover el estado hacia el ancestro común más bajo que necesita leer o modificar ese estado. En lugar de que cada composable hijo tenga su propio remember, el padre tiene el estado y lo pasa hacia abajo como parámetros.

El patrón es: el padre pasa el valor (val) y una función lambda para modificarlo (onValueChange). El hijo es "stateless" — no sabe de dónde viene el valor ni dónde se guarda.

¿Por qué importa? Si dos composables hijos necesitan compartir el mismo estado, si cada uno tiene su remember propio, son variables independientes que nunca se sincronizan. Elevando el estado al padre, ambos hijos leen la misma variable. Además, los composables sin estado son más fáciles de reutilizar y de testear.

data class Materia(val nombre: String, val nota: Double, val aprobada: Boolean)

fun calcularPromedio(materias: List<Materia>): Double {
    val total = materias.size
    if (total == 0) return 0.0
    val suma = materias.sumOf { it.nota }
    return (suma / total)           // error A
}

@Composable
fun PantallaMaterias() {
    val materias = mutableListOf(   // error B
        Materia("Análisis", 7.5, true),
        Materia("Álgebra",  4.0, true),
        Materia("Física",   3.5, false)
    )
    var filtro = "todas"            // error C
    val promedio = calcularPromedio(materias)

    Column(modifier = Modifier.fillMaxWidth().padding(16.dp)) {
        Text("Promedio: $promedio")
        LazyColumn {
            materias.forEach { m -> MateriaItem(m) }  // error D
        }
    }
}

@Composable
fun MateriaItem(m: Materia) {
    Text("${m.nombre}: ${m.nota}")
}
A
División entera: suma es Double pero total es Int. En Kotlin la división Double / Int sí da Double correctamente, pero si la función fuera suma.toInt() / total o ambas fueran Int, daría resultado truncado. El bug real aquí es que suma / total podría entenderse ambiguo — lo correcto y explícito es suma / total.toDouble() para dejar claro la intención de división decimal.
B
mutableListOf no observable: Agregar o quitar materias no dispara recomposición. Debe ser remember { mutableStateListOf(...) }.
C
var filtro = "todas" sin remember: Variable local que se reinicia en cada recomposición. No puede usarse para guardar el estado del filtro entre interacciones. Debe ser var filtro by remember { mutableStateOf("todas") }.
D
forEach dentro de LazyColumn: Debe usarse items(materias) { m -> MateriaItem(m) }. Con forEach, Compose no puede reciclar los ítems ni usar key para optimizar recomposición.
✔ Correcciones clave

    Materia("Análisis", 7.5, true), ...
) }

    items(materias) { m -> MateriaItem(m) }        // D
}
Conversor de temperatura
Lógica de cálculo, TextField y when
4 errores 
fun convertir(valor: Double, desde: String, hacia: String): Double {
    return when {
        desde == "C" && hacia == "F" -> valor * 9 / 5 + 32
        desde == "F" && hacia == "C" -> (valor - 32) * 5 / 9
        desde == "C" && hacia == "K" -> valor + 273.15
        // falta else                // error A
    }
}

@Composable
fun Conversor() {
    var entrada = ""                 // error B
    var resultado by remember { mutableStateOf("") }

    OutlinedTextField(
        value = entrada,
        onValueChange = { entrada = it },
        label = { Text("Temperatura en °C") }
    )

    Button(onClick = {
        val num = entrada.toDouble()  // error C
        resultado = convertir(num, "C", "F").toString()
    }) { Text("Convertir") }

    Text("Resultado: $resultado")
}

@Preview
fun ConversorPreview() {            // error D
    Conversor()
}
A
Falta rama else en when usado como expresión: El when devuelve un valor (Double), por lo que debe ser exhaustivo. Si ninguna condición coincide (ej: "K" a "F"), el compilador no acepta el código. Debe agregarse else -> valor.
B
var entrada = "" sin remember: Variable local sin estado observable. El TextField no puede mostrar lo que el usuario tipea porque se reinicia en cada recomposición. Debe ser var entrada by remember { mutableStateOf("") }.
C
toDouble() sin manejo de null: Si el campo está vacío o contiene letras, lanza NumberFormatException y la app crashea. Debe ser toDoubleOrNull() ?: 0.0.
D
Falta @Composable en la función Preview: ConversorPreview() llama a Conversor() que es @Composable. Sin la anotación, el compilador rechaza la llamada.
✔ Correcciones clave
return when { ...; else -> valor }           // A
var entrada by remember { mutableStateOf("") } // B
val num = entrada.toDoubleOrNull() ?: 0.0      // C
@Preview @Composable                           // D
fun ConversorPreview() { Conversor() }
