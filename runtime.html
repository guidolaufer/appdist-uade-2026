⚙️ JIT vs AOT — Compilación en Runtime

Just-In-Time vs Ahead-Of-Time · Modelo híbrido desde Android 7 · UADE 2026

JIT — Just-In-Time Compilation

JIT compila el bytecode (.dex) a código máquina nativo EN EL MOMENTO en que se va a ejecutar, durante la ejecución de la app.

¿Cómo funciona?

App se inicia
    ↓
ART empieza a INTERPRETAR el bytecode .dex
    ↓
JIT compiler monitorea cuál código se ejecuta frecuentemente
("hot code" = código caliente = muy usado)
    ↓
Cuando detecta hot code → lo compila a código máquina nativo
    ↓
Las próximas ejecuciones usan el código nativo (más rápido)
    ↓
El código compilado se guarda en memoria RAM (NO en disco)
→ Se pierde al cerrar la app / reiniciar el dispositivo

Ventajas del JIT

✅ Instalación RÁPIDA — no compila nada al instalar, solo copia el APK
✅ Menor uso de almacenamiento — no guarda código nativo compilado
✅ Optimizaciones dinámicas — puede optimizar según cómo USA
   realmente la app (qué código es hot code)
✅ Menor tiempo hasta primera ejecución de la app

Desventajas del JIT

❌ Mayor uso de CPU al arrancar — tiene que compilar mientras ejecuta
❌ Mayor uso de RAM — mantiene el compilador en memoria
❌ Arranque más lento las primeras veces
❌ Comportamiento inconsistente — el primer arranque es más lento
   que los siguientes (warm-up period)
❌ Consumo de batería al compilar en background
JIT fue el modelo de Dalvik (Android 1 hasta Android 4.4). La experiencia era "laggy" comparada con iOS, precisamente por este warm-up inicial.

AOT — Ahead-Of-Time Compilation

AOT compila el bytecode .dex a código máquina nativo ANTES de la primera ejecución, generalmente durante la instalación de la app.

¿Cómo funciona?

Se instala el APK
    ↓
dex2oat convierte TODO el bytecode .dex → código máquina nativo
(esto ocurre durante la instalación, puede tardar varios segundos)
    ↓
El código compilado se guarda en disco como archivo .oat
    ↓
Cuando se abre la app → ART ejecuta directamente el código nativo
sin necesidad de compilar nada
    ↓
Arranque rápido, ejecución rápida siempre

Ventajas del AOT

✅ Ejecución MÁS RÁPIDA — código ya compilado, sin warm-up
✅ Arranque consistente — siempre el mismo rendimiento
✅ Menor uso de CPU durante la ejecución
✅ Mejor experiencia de usuario (sin lag inicial)
✅ Menor consumo de batería durante el uso normal

Desventajas del AOT

❌ Instalación LENTA — compilar toda la app tarda tiempo
❌ Mayor uso de almacenamiento — guarda el código nativo en disco
   (puede ser 2-3x el tamaño del APK original)
❌ Sin optimizaciones dinámicas — compila basándose en el código
   estático, no sabe cómo usará la app el usuario real
❌ Updates lentos — hay que recompilar en cada actualización
AOT fue introducido con ART en Android 5.0 (Lollipop). La instalación se volvió más lenta pero la experiencia de uso mejoró notablemente — Google lo popularizó con el slogan "smoother, faster".

Modelo Híbrido — Android 7.0+ (Nougat)

Desde Android 7, Google introdujo un modelo que combina JIT y AOT para obtener lo mejor de ambos mundos.

PRIMERA INSTALACIÓN:
    APK instalado sin compilación AOT completa
    → Instalación rápida ✅

PRIMERAS EJECUCIONES (JIT activo):
    ART usa JIT para compilar hot code en RAM
    JIT también guarda un "perfil de uso" (.prof)
    → El perfil registra qué código se usa más

DISPOSITIVO EN REPOSO + CARGANDO (AOT selectivo):
    dex2oat lee el perfil de uso (.prof)
    Compila a AOT SOLO el código marcado como hot code
    Guarda en disco (.odex / .vdex)
    → Solo compila ~20-30% del código total

EJECUCIONES SIGUIENTES:
    El código hot (compilado AOT) corre nativo → rápido
    El código frío (poco usado) sigue con JIT
    → Lo mejor de ambos mundos ✅
Resultado del modelo híbrido:
🚀 Instalación rápida (como JIT puro)
💾 Menor uso de almacenamiento (solo compila el hot code, ~20-30%)
⚡ Rendimiento excelente (el código más usado corre en AOT)
🔋 Bajo consumo (AOT se ejecuta solo cuando está cargando y en reposo)

🧠 Quiz — JIT vs AOT

¿Por qué Android 7 no usa AOT puro si es más rápido en ejecución?
Porque AOT puro tiene dos problemas críticos en mobile: (1) instalación lenta — compilar toda la app al instalar puede tardar minutos, lo cual es inaceptable para el usuario; (2) mayor uso de almacenamiento — el código nativo compilado puede ocupar 2-3x el espacio del APK original, problemático en dispositivos con poco storage. El modelo híbrido resuelve ambos problemas compilando solo el hot code (20-30%) y haciéndolo cuando el dispositivo está en reposo y cargando.
¿Qué es el "warm-up period" de JIT y por qué afecta la experiencia?
El warm-up period es el tiempo inicial donde JIT todavía está detectando cuál es el hot code. Durante este período, el código se interpreta (más lento) o se compila on-the-fly (usa CPU). El usuario nota lag, frames perdidos, o animaciones lentas en los primeros segundos de uso de la app. A medida que JIT aprende el patrón de uso, el rendimiento mejora. En AOT no existe este período porque el código ya está compilado antes de la primera ejecución.
¿Qué es dex2oat?
dex2oat es la herramienta de Android que realiza la compilación AOT: toma archivos .dex (bytecode Dalvik) y los convierte en código máquina nativo para el procesador del dispositivo (archivo .odex u .oat). Se ejecuta durante la instalación de la app (AOT completo en versiones antiguas) o en background cuando el dispositivo está en reposo y cargando (AOT selectivo/guiado por perfil en Android 7+). El nombre viene de "dex to oat" (dex → oat format).
