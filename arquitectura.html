Las 5 capas de la arquitectura Android

Android está organizado en capas apiladas. Cada capa provee servicios a la capa superior y consume servicios de la inferior.

🔵 Capa 5 — Applications (Aplicaciones)

Es la capa más alta. Contiene todas las apps instaladas: el teléfono, el navegador, los contactos, el calendario, y también tus propias apps. Es lo que el usuario ve y toca directamente.

Ejemplos: Gmail, Chrome, tu app Android que estás desarrollando.

🟢 Capa 4 — Application Framework

Provee APIs de alto nivel para que los desarrolladores construyan apps. Incluye managers y providers que exponen funcionalidades del sistema operativo.

Componentes clave: Activity Manager (ciclo de vida), Window Manager (ventanas), Content Providers (datos compartidos), View System (UI), Notification Manager, Location Manager, Package Manager.

🟠 Capa 3 — Libraries + Android Runtime

Dos subsistemas en paralelo:

Libraries (C/C++): SQLite, OpenGL ES, WebKit, Media Framework, libc. Son librerías nativas compiladas para el hardware específico.

Android Runtime (ART): máquina virtual que ejecuta el bytecode de las apps (archivos .dex). Gestiona la memoria con garbage collector, ejecuta el código con JIT/AOT.

🟣 Capa 2 — Hardware Abstraction Layer (HAL)

Define interfaces estándar que permiten al Application Framework acceder al hardware sin conocer los detalles de implementación. Cada fabricante implementa el HAL para su hardware específico.

Módulos HAL: cámara, bluetooth, audio, sensores, GPS, radio.

🔴 Capa 1 — Linux Kernel

La base de todo el sistema. Maneja drivers de hardware, gestión de memoria, gestión de procesos, red, seguridad y el modelo de permisos. Android usa una versión modificada del kernel de Linux.

Drivers incluidos: pantalla, cámara, flash, audio, WiFi, Bluetooth, binder (IPC).

Mnemónico para recordar el orden (de abajo hacia arriba):
Linux → HAL → Libraries+Runtime → Framework → Apps
"Los Hackers Linkearon el Framework de Android"

¿Cómo interactúa el desarrollador con cada capa?

Capa¿Cómo interactúa el desarrollador?Ejemplo concreto
Applications Directamente — el dev construye la app que vive en esta capa Crear una Activity, escribir el código Java/Kotlin
App Framework Usando las APIs del SDK de Android (clases Java/Kotlin) getSystemService(LOCATION_SERVICE), startActivity(intent), usar RecyclerView
Libraries Indirectamente a través del Framework, o directo con NDK/JNI para C/C++ Usar Room Database (sobre SQLite), reproducir video (Media Framework), código nativo con NDK
HAL No se accede directamente — el Framework abstrae el hardware Usar CameraManager sin saber qué cámara tiene el dispositivo
Linux Kernel No se accede desde apps normales. Solo fabricantes y ROM developers Compilar un driver personalizado (requiere permisos root)
Regla práctica: el desarrollador de apps trabaja casi exclusivamente con las capas Application Framework y Applications. El resto está encapsulado por el sistema.

🧠 Quiz — Arquitectura Android

¿Por qué Android usa .dex en vez de bytecode JVM estándar?
El bytecode JVM (.class) fue diseñado para computadoras de escritorio con memoria y CPU abundante. Android corre en dispositivos con recursos limitados. El formato .dex (Dalvik Executable) está optimizado para: (1) menor uso de memoria — múltiples clases se agrupan en un solo .dex; (2) mejor rendimiento en ARM; (3) compartir clases entre procesos de forma eficiente. Además, Dalvik/ART fue diseñado desde cero para mobile.
¿Para qué sirve el AndroidManifest.xml?
Es el "contrato" de la app con el sistema Android. Declara: (1) todas las Activities, Services, Receivers y Content Providers de la app; (2) los permisos que la app necesita (cámara, internet, GPS); (3) el package name único de la app; (4) la versión mínima de Android requerida; (5) los intent-filters (qué intents puede manejar la app). Sin el Manifest, Android no sabe cómo tratar la app.
¿Qué es el Binder y para qué sirve?
El Binder es el mecanismo de IPC (Inter-Process Communication) de Android, implementado como driver en el Linux Kernel. Permite que los procesos de Android se comuniquen entre sí de forma eficiente y segura. Lo usás cuando tu app llama a un servicio del sistema (como el GPS o la cámara) — tu proceso se comunica con el proceso del sistema a través del Binder. También es la base de AIDL (Android Interface Definition Language).
¿Qué diferencia hay entre Dalvik y ART?
Dalvik (hasta Android 4.4): la VM original de Android. Usaba JIT (Just-In-Time) — compilaba el bytecode .dex a código máquina en tiempo de ejecución, cada vez que corrías la app. Mayor uso de CPU al arrancar.

ART (Android 5+ en adelante): la VM actual. Usa AOT (Ahead-Of-Time) — compila el .dex a código nativo durante la instalación. Arranque más rápido, mejor rendimiento, mayor uso de almacenamiento. Desde Android 7, usa un modelo híbrido JIT+AOT.
