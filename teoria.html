Android SDK, AVD, Emulador y Android Studio

Diferencias y relación entre las herramientas de desarrollo

ConceptoQué esAnalogía
Android SDK Software Development Kit. Conjunto de herramientas, librerías, APIs y compiladores que permiten construir apps Android. Incluye el compilador d8, las APIs del sistema (WiFi, cámara, GPS…), herramientas de línea de comandos (adb, aapt2) y las imágenes del sistema para el emulador. La caja de herramientas completa del carpintero: serruchos, clavos, barniz…
AVD Android Virtual Device. Una configuración que define las características del dispositivo virtual: modelo de teléfono o tablet, tamaño de pantalla, API level (versión de Android), RAM, almacenamiento. Es básicamente un archivo de configuración. La ficha técnica que describe cómo es el dispositivo (como las especificaciones de un celular).
Emulador El programa que ejecuta un AVD. Crea una máquina virtual Android basada en la configuración del AVD y la ejecuta en tu computadora. Usa QEMU internamente para virtualizar el procesador ARM. El AVD define el "qué", el emulador es el "cómo". El motor que arranca el dispositivo descrito en la ficha técnica.
Android Studio IDE (Entorno de Desarrollo Integrado) basado en IntelliJ IDEA. Integra el SDK, gestiona los AVDs, provee editor de código con autocompletado Kotlin, Layout Inspector, Logcat, Profiler, el Preview de Compose y el Device Manager. Es la interfaz gráfica que une todo. El taller del carpintero donde están todas las herramientas organizadas y al alcance.
❓ Pregunta típica de parcial: "¿Es lo mismo el AVD y el emulador?"
No. El AVD es la definición del dispositivo virtual (sus características). El emulador es el programa que ejecuta esa definición. Podés tener múltiples AVDs (Pixel 6 con API 34, Pixel 4 con API 30) y el emulador los ejecuta de a uno a la vez.
❓ "¿Qué diferencia hay entre ejecutar en el emulador y en un dispositivo físico?"
El emulador virtualiza el hardware en tu PC, lo que es más lento pero conveniente. Un dispositivo físico ejecuta en hardware real, con sensores reales, mejor performance y casos edge que el emulador no replica perfectamente (GPS, notificaciones push, NFC, etc.).
❓ "¿Qué es el API Level?"
Un número que identifica la versión del Android SDK. Cada versión de Android tiene un API Level: Android 14 = API 34, Android 13 = API 33, etc. Las apps declaran un minSdk (mínimo para instalar) y targetSdk (optimizado para). Cuanto mayor el API Level, más funcionalidades disponibles pero menos dispositivos compatibles.

¿Qué es @Composable?

La unidad básica de UI en Jetpack Compose

Una función marcada con @Composable es una función especial que Compose sabe cómo invocar para emitir elementos de UI. No devuelve una vista (como hacía el sistema de Views), sino que describe cómo debería verse la interfaz dado el estado actual.

@Composable
fun Saludo(nombre: String) {
    Text("Hola, $nombre!")  // describe qué mostrar
}

Características clave de una función @Composable:

Solo puede llamarse desde otra @Composable

No se puede invocar desde una función Kotlin ordinaria. Es un contrato del compilador.

No retorna nada útil

Retorna Unit (o implícitamente nada). Su efecto es emitir nodos de UI al árbol de composición.

Puede reejecutarse en cualquier momento

Compose puede llamarla de nuevo cuando el estado cambie (recomposición). Debe ser idempotente: el mismo estado siempre produce la misma UI.

Puede tener efectos secundarios controlados

Solo a través de APIs específicas: remember, LaunchedEffect, SideEffect, etc.

❓ "¿Por qué @Composable es una anotación y no una interfaz o clase?"
Porque modifica el comportamiento del compilador. El compilador de Compose (un plugin del compilador de Kotlin) transforma las funciones @Composable para inyectarles un parámetro especial (Composer) de forma transparente. Esto permite rastrear el estado del árbol de composición, identificar qué partes cambiaron y hacer recomposición eficiente.

Modelo declarativo vs. imperativo

Por qué Compose es "declarativo" y qué significa eso

Imperativo (View system)Declarativo (Jetpack Compose)
Concepto Describís cómo cambiar la UI paso a paso. Describís qué debe mostrar la UI dado un estado.
Ejemplo textView.text = "Hola"
textView.visibility = VISIBLE
button.setOnClickListener { ... }		 Text("Hola") dentro de una función que se re-llama cuando el estado cambia.
Actualización Vos manipulás el árbol de Views manualmente (findViewById, etc.). Compose re-ejecuta las funciones afectadas automáticamente cuando el estado cambia (recomposición).
Estado Disperso en el código: variables, listeners, callbacks. Centralizado con remember y mutableStateOf. La UI es función del estado: UI = f(estado).
Problemas típicos Inconsistencias entre estado interno y lo que muestra la UI, bugs de sincronización. Recomposición excesiva si no se maneja bien el estado.
Frase clave para el parcial: En el modelo declarativo, la UI es una función pura del estado. Cuando el estado cambia, Compose invoca automáticamente las funciones @Composable afectadas para reconstruir la interfaz. El desarrollador nunca manipula la UI directamente.

Cómo organizar arquitectónicamente una app

Separación de capas y principio de responsabilidad única

Android recomienda la arquitectura en capas, siguiendo el principio de que cada parte del código tenga una sola responsabilidad. El patrón más usado en apps Compose es MVVM (Model-View-ViewModel) o una variante simplificada con capas UI / Lógica / Datos.

UI
Capa de UI — @Composable functions, pantallas, componentes visuales.
Solo muestra datos y captura eventos del usuario. No tiene lógica de negocio.
↕
L
Capa de Lógica / ViewModel — Funciones de cálculo, filtrado, transformación.
Procesa los datos, expone el estado a la UI. No conoce cómo se ve la UI.
↕
D
Capa de Datos — Repository, data classes, fuentes de datos (API, BD, archivos).
Provee los datos. No sabe nada de la UI ni de la lógica.

En el proyecto PokeCompose del parcial, la separación ya está esbozada:

ArchivoCapaResponsabilidad
Pokemon.ktDatosData class que modela un Pokémon
PokemonRepository.ktDatosProvee la lista de 251 Pokémon
PokemonLogic.ktLógicaCálculos: porcentaje, restantes, clasificación, búsqueda
PokemonScreen.ktUI@Composable que muestra la Pokédex y captura interacciones
MainActivity.ktUI (entrada)Entry point de la Activity, inicializa el tema y llama PokemonScreen
❓ Caso típico de examen: "Dada esta app de turnos médicos, ¿cómo la organizarías en capas?"
Datos: data class Turno(id, fecha, paciente, medico) + TurnoRepository (lista en memoria o llamada a API).
Lógica: TurnoLogic con funciones como filtrarPorFecha(), calcularDemora(), ordenarPorHora().
UI: TurnosScreen (lista de turnos), TurnoItem (fila individual), FiltrosBar (barra de búsqueda), cada una @Composable.

Elementos de Material Design 3 en Compose

Componentes, colores y tipografía del sistema de diseño de Google

Material Design 3 (Material You) es el sistema de diseño de Google. En Jetpack Compose se accede a sus componentes importando androidx.compose.material3.*. Organiza la UI en componentes reutilizables con semántica definida.

Scaffold

Estructura base de pantalla. Provee slots para topBar, bottomBar, floatingActionButton y el contenido principal con padding correcto.

TopAppBar

Barra superior con título, íconos de navegación y acciones. Variantes: CenterAlignedTopAppBar, MediumTopAppBar.

Card

Contenedor con elevación y bordes redondeados. Agrupa información relacionada. Soporta onClick para hacerla clickeable.

Button / OutlinedButton / TextButton

Button = acción primaria (fondo sólido). OutlinedButton = acción secundaria. TextButton = acción terciaria o menor énfasis.

OutlinedTextField / TextField

Campos de entrada de texto. OutlinedTextField tiene borde visible. Soportan label, placeholder, isError, supportingText.

LazyColumn / LazyRow

Listas de scroll eficientes (equivalente a RecyclerView). Solo renderizan los ítems visibles. Usan items() y opcionalmente key.

MaterialTheme

Punto de acceso al tema: MaterialTheme.colorScheme, MaterialTheme.typography, MaterialTheme.shapes. Permite temas claro/oscuro dinámicos.

Text

Muestra texto. Acepta style = MaterialTheme.typography.bodyMedium, fontSize, fontWeight, color, maxLines, overflow.

ColorScheme en Material 3: Los colores tienen nombres semánticos: primary (color principal), onPrimary (texto sobre primary), surface (fondo de cards), onSurface (texto sobre surface), error, background. Nunca hardcodees colores en los componentes si podés usar el ColorScheme — así la app respeta el modo oscuro automáticamente.
❓ "¿Qué es un Modifier y para qué sirve?"
Modifier es una cadena inmutable de instrucciones que modifican cómo se mide, dibuja o se comporta un Composable. Se encadena con .: Modifier.fillMaxWidth().padding(16.dp).clickable { ... }. El orden importa: padding().background() dibuja el fondo solo en el área interior, mientras que background().padding() cubre todo el área incluyendo el padding.

¿Por qué no se recomienda que las funciones Composable sean grandes?

Recomposición, legibilidad y responsabilidad única

Esta es una de las preguntas más frecuentes en el parcial teórico. Hay tres razones principales:

1. Recomposición ineficiente

Cuando una variable de estado cambia, Compose re-ejecuta la función completa que la contiene. Si toda la app está en una sola función gigante, cualquier cambio (el usuario escribe una letra) recalcula y redibuja toda la pantalla. Con funciones pequeñas, solo se re-ejecutan las que leen el estado que cambió.

2. Violación de responsabilidad única

Una función grande mezcla la lógica del header, la lista, los filtros y los botones. Si hay un bug en la lista, tenés que buscar entre 200 líneas. Funciones pequeñas y con nombre descriptivo (PokemonItem, BuscadorBar, ProgresoCard) hacen el código legible y navegable.

3. Reutilización imposible

Una función enorme no puede reutilizarse en otra pantalla. Si extraés PokemonItem(pokemon) como función separada, podés usarla en la lista principal, en una pantalla de favoritos, en una búsqueda, etc.

4. Dificultad para hacer Preview

Una función con 20 parámetros de estado es difícil de previsualizar. Una función pequeña con pocos parámetros se puede testear con @Preview en segundos.

Regla práctica: Si una función @Composable hace más de una cosa (mostrar datos + manejar estado + calcular algo), probablemente deba dividirse. Una función bien diseñada cabe en ~20–30 líneas. 
// ❌ MAL: todo en una sola función gigante
@Composable
fun PantallaCompleta() {
    // 200 líneas de layouts, estados, cálculos...
}

// ✔ BIEN: responsabilidades separadas
@Composable
fun PantallaPokedex() {
    ProgresoCard(capturados, total)   // solo muestra el progreso
    BuscadorBar(busqueda, onChange)   // solo maneja la búsqueda
    ListaPokemon(lista, onCapturar)   // solo renderiza la lista
}
@Composable fun ProgresoCard(...) { /* ≈20 líneas */ }
@Composable fun BuscadorBar(...) { /* ≈15 líneas */ }
@Composable fun ListaPokemon(...) { /* ≈25 líneas */ }

Kotlin: scripts y archivos .kts

Diferencia entre código Kotlin de app y Kotlin Script

En un proyecto Android aparecen dos tipos de archivos Kotlin:

Kotlin (.kt)Kotlin Script (.kts)
Uso Código de la app: Activities, ViewModels, data classes, composables. Scripts de configuración y automatización: build.gradle.kts, settings.gradle.kts, libs.versions.toml.
Se ejecuta cuando Al correr la app en el dispositivo o emulador. Al hacer build/sync del proyecto en Android Studio.
Ejemplos MainActivity.kt, PokemonScreen.kt app/build.gradle.kts, gradle/libs.versions.toml
Diferencia principal Necesita compilarse a .dex para correr en Android. Es interpretado por Gradle al momento de configurar el proyecto.

El archivo build.gradle.kts es el más relevante en el parcial. Declara:

// app/build.gradle.kts
android {
    compileSdk = 34
    defaultConfig {
        minSdk = 24          // versión mínima de Android para instalar
        targetSdk = 34       // versión para la que está optimizada
        versionCode = 1
        versionName = "1.0"
    }
}
dependencies {
    implementation("androidx.compose.material3:material3")
    implementation("io.coil-kt:coil-compose:2.6.0")
}
❓ "¿Para qué sirve el archivo AndroidManifest.xml?"
Declara la estructura de la app ante el sistema Android: qué Activities existen, cuál es el punto de entrada principal (android.intent.action.MAIN), qué permisos requiere la app (internet, cámara, etc.), qué servicios y receivers tiene. Android lee el Manifest al instalar y al lanzar la app.
